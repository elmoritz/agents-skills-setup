# Init — the bundle itself: where it came from, and refreshing it

Read by `/ticket-init` in two places: the apply phase of a fresh init (record
where the bundle came from) and the first step of update mode (refresh it).
This is what makes a separate "update the bundle" step unnecessary: re-running
init brings the commands, skills, references and `te` up to the template's
latest version **and** regenerates the project's agents against them, in one
run.

<!-- sync:divergent -->
Gates here are numbered lists, like every init gate: the user replies with the number.
<!-- sync:end -->

## What the bundle ships, and what the project owns

`.agents/scripts/te bundle diff` decides this, so it is never judged by eye:

- **Shipped** — everything the template keeps in this bundle's directory
  (commands, skills, references, scripts, README, settings) and, for the
  `.agents` bundle, `AGENTS.md` and the command routers in `.gemini/commands/`.
- **Owned by the project, never refreshed** — `agents/` (generated per
  project; update mode refreshes their *contracts* from the new kinds instead),
  `config.yaml`, and `setup/`. Subagent routers are regenerated by
  `te routers write`, not copied.

## The template source

The default source is **https://github.com/elmoritz/agents-skills-setup**. A
project copied from a fork records the fork instead — the manifest's
`bundle.source` always wins over the default.

## Getting a checkout

Everything below needs the template on disk:

```sh
tpl=$(mktemp -d)/template
git clone --depth 1 <source> "$tpl"                    # latest
git -C "$tpl" rev-parse HEAD                            # its commit
```

and, when the manifest records a `bundle.commit`, the template **as it was** at
that commit — the base that tells "the template changed this" from "the project
changed this":

```sh
base=$(mktemp -d)/base
git init -q "$base" && git -C "$base" fetch -q --depth 1 <source> <bundle.commit> && git -C "$base" checkout -q FETCH_HEAD
```

The orient phase's `template` probe (`git ls-remote <source> HEAD`) says whether
any of this is reachable. Remove both checkouts when done.

## On a fresh init: record the provenance

In the apply phase, before writing the manifest, clone the latest template and
run `.agents/scripts/te bundle diff --template "$tpl"` against the bundle as it
was copied:

- **`changed=0`** — the copy is exactly the template's latest. Record it:

  ```yaml
  bundle:
    source: "<source>"
    commit: "<git -C $tpl rev-parse HEAD>"
    checked_at: "<ISO 8601>"
  ```

- **Anything changed** — the bundle came from somewhere else, or was edited
  before init. Gate (numbered list):
  - **question:** "This bundle doesn't match the template's latest version. Where did it come from?"
  - **header:** "Bundle source"
  - **options:**
    - **The default template (Recommended)** — record the default source with `commit: unknown`; the first update will ask about each differing file once.
    - **A fork** — free-text follow-up for its URL; re-run the comparison against it.
    - **Don't track it** — omit the `bundle:` block; update mode will not refresh the bundle.
- **`template` probe `unavailable`** — record `source` with `commit: unknown`
  and say so; the first update with network access settles it.

## In update mode: refresh the bundle

Skip this step, saying why, when the manifest has no `bundle:` block or the
`template` probe is `unavailable` (then it is a *pending* line). Otherwise:

1. **Check.** Clone the latest template; if its HEAD equals `bundle.commit`,
   the bundle is current — move on. Otherwise fetch the base (when
   `bundle.commit` is a SHA) and run
   `.agents/scripts/te bundle diff --template "$tpl" [--base "$base"]`.
2. **Classify every line** it prints:

   | Status | Action |
   | --- | --- |
   | `upstream-changed`, `new-upstream`, `removed-upstream` | Take the template's version (or delete). The project never touched these. |
   | `local-changed`, `local-only`, `deleted-locally` | Keep the project's state — upstream did not change them, or the project chose to. |
   | `both-changed`, `removed-upstream-edited`, `differs` | **Gate per file** (below). |

   For `differs` (no base to attribute it — the commit was `unknown`), offer
   **Take the template's version for all differing files** first, since a copy
   that was never edited is the common case.
3. **The per-file gate.** Show the diff (project vs template), then gate
   (numbered list):
   - **question:** "`<path>` changed both here and in the template. Which version?"
   - **header:** "Bundle file"
   - **options:**
     - **Merge (Recommended)** — keep the project's change and apply the template's on top; show the result.
     - **Take the template's** — replace the file.
     - **Keep mine** — leave it; the next update will ask again only if the template changes it again.
4. **Show the summary** — files taken, kept, merged, deleted — and gate once
   (**Apply the bundle refresh** / **Skip it this time**). Nothing is written
   before this gate.
5. **Write** the chosen files (preserving `te`'s exec bit — `chmod +x
   .agents/scripts/te`), set `bundle.commit` to the template's HEAD and
   `bundle.checked_at` to now, and commit **on its own**:

   ```
   ticket: init — bundle refresh to <short sha> (<n> files)
   ```

   The bundle refresh is its own commit so the template's changes stay
   reviewable apart from the project's regenerated agents.
6. **Restart from the new instructions.** The refresh may have changed this
   very skill. Re-read the spine and `.agents/references/init/update.md` from
   disk and continue update mode from the step after this one — never from
   what you remember of the old text. The spine is:
<!-- sync:divergent -->
   `.agents/skills/ticket-init/SKILL.md`.
<!-- sync:end -->

When the project serves both bundles, refresh each with its own `te`.
