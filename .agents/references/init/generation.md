# Init — designing and generating the agents

Read by `/ticket-init` in its agent-design phase. There is no fixed catalog of
research agents: the set is **designed for this project** from what the
discover phase found and what the research phase learned, then each agent is
**generated** from a kind (`.agents/references/agents/kinds/`) following the
anatomy in `.agents/references/agents/anatomy.md`. Read the anatomy before
writing the first agent.

## 1. Existing agents

List the agent files already in `.agents/agents/`. Sort them into:

- **Generated by init** — they carry an `<!-- agent-kind: … -->` marker. On a
  fresh init there should be none; if there are, they come from a copied
  bundle — treat them as existing hand-written agents below.
- **Hand-written** — everything else. Gate (numbered list, multi-select):
  - **question:** "Found existing agents. Which should ticket creation dispatch as research agents?"
  - **header:** "Existing"
  - **options:** one per agent (label = name, description = its frontmatter description, truncated).

  Each selected one is registered in `research.agents` with a `consult` hint
  derived from its description (confirm it inline if unclear). Hand-written
  agents are **never rewritten** — init registers them and leaves the file alone.

## 2. Design the research set

A research agent owns **one source of information** that ticket creation would
otherwise read inline, again and again. Design the set from the evidence, one
candidate per source, considering at least:

| Source | Propose when | Knowledge comes from |
|---|---|---|
| The stack's performance profile | there are researched subjects (almost always) | the `pitfalls` notes of every subject |
| The language(s) and their idioms | there are researched subjects (almost always) | the `idioms` and `security` notes |
| This repository's precedent and past tickets | the repository has history worth mining | read live — `git log`, the ticket root |
| Internal docs, ADRs, runbooks | a `docs` or `references.architecture` fact exists | read live — the documented paths |
| A central library's API at its locked version | research found a library whose API most work touches | its `idioms` / `tooling` notes plus the docs site |
| A design source | a `design_source` fact exists | read live — the design tool or its MCP server |
| The open web | always worth offering; the user decides | none — it searches at run time |

Merge candidates that would share one source; split one whose source is really
two. Name each in kebab case after its source (`perf-expert`,
`typescript-expert`, `adr-researcher`) — never a name already taken in
`.agents/agents/` by a hand-written agent.

Show the proposed set as a table — name · source · `consult` hint · the
research subjects feeding its knowledge — then gate (numbered list):

- **question:** "These are the research agents I'd generate for this project. Go ahead?"
- **header:** "Agents"
- **options:**
  - **Generate these (Recommended)** — every proposed agent is generated.
  - **Remove some** — free-text follow-up naming which; re-show and re-gate.
  - **Add a source** — free-text follow-ups: what the source is, how to reach it (path / URL / MCP tool), and when ticket creation should consult it. Re-show and re-gate.

Generating none is a legitimate answer: `research.agents` is omitted and ticket
creation reads sources inline.

## 3. Generate each agent

Write each agent to a **scratch directory** (`mktemp -d`), not to
`.agents/agents/` — nothing is written into the repository before the user
approves the assembled config. For each one:

1. Start from the anatomy's skeleton and the `research` kind.
2. Paste the contract regions exactly as `.agents/scripts/te agent contract research` prints them.
3. Write the generated regions per the kind's guidance — `role`, `source`,
   `method`, `knowledge` — with every research finding carried over **with its
   source**, specific to this project's stack and versions.
4. Frontmatter: `name`, a one-sentence `description` that says when ticket
   creation consults it, and the bundle's agent line from the anatomy (an agent
   whose source is on the web also gets the web tools).
5. Leave the user region empty.
6. Run `.agents/scripts/te agent check <file> --kind research`. Fix and re-run
   until it prints `ok=true`; keep the printed hashes for the manifest.

When `subagents` is `verified`, generate agents in parallel — one subagent per
agent, each handed its kind, the anatomy, its research notes and its source
description — and run `te agent check` on each result yourself.

## 4. Record the set

- **Config:** each generated or registered agent becomes a `research.agents`
  entry — `name` plus a one-line `consult` hint (when ticket creation should
  dispatch it, e.g. `"the work could affect latency, memory, or throughput"`).
- **Manifest:** each *generated* agent gets an `agents:` entry
  (`.agents/references/init/manifest.md`) — name, kind, path, `generated_at`,
  `research` (`done` when its knowledge came from `done` subjects, `thin` when
  any feeding subject was thin, `none` when it reads its source live), the
  research subject ids that fed it, and the region hashes `te agent check`
  printed.

**Gate:** every agent in the approved set passed `te agent check` in the
scratch directory.
